# Сопровождение

## Регулярное обновление

```bash
make catalog fetch-files fetch-db build docs test
```

* `catalog` заново обходит страницы на трёх языках. Новые файлы и новые годы в формах веб-БД
  подхватываются автоматически (`data/catalog/files.json`, `data/catalog/db_options/*.json`).
  Изменения манифестов видны в `git diff` — это удобный способ заметить, что на сайте что-то поменялось.
* `fetch-files` скачивает только отсутствующие файлы (`--force` — все заново). Хэши — в `files.json`.
* `fetch-db` докачивает отсутствующие годы и **всегда** перезапрашивает два последних года
  (`--refresh-last 2`), т. к. текущий и прошлый годы уточняются. Уже скачанные выгрузки
  перепроверяются; некорректные запрашиваются заново. Можно ограничить: `--nid 148 --lang en --mode annual`.
* `build` пересоздаёт БД целиком (около 5 минут).
* После сборки проверьте `SELECT * FROM qc_summary` (см. [data_quality.md](data_quality.md))
  и запустите `make test`.

Рекомендуемая периодичность — ежемесячно (месячные данные публикуются с лагом ~1–2 мес.;
годовые файлы по ТН ВЭД появляются в течение следующего года).

## Что делать, если…

**Появился новый файл неизвестной структуры.** Семейство определяется по странице (`FAMILY_BY_NID`
в `build.py`). Все ячейки в любом случае попадут в `raw_xlsx_cell`. Если у нового 2-значного
бюллетеня появился лист с новым названием, он классифицируется в `files_hs2.classify_sheet`
(по умолчанию — `hs2_partner`); при необходимости добавьте правило и тип листа.

**Не сопоставились названия стран** (`qc_unresolved_country`, `partner_rows_without_country`).
Добавьте написание в `reference.COUNTRY_NAME_ALIASES` (ключ — название как в источнике,
значение — код страны). Проверить код можно запросом к веб-БД с конкретным `thid[]`.

**Выгрузка веб-БД отклоняется** (`export ... rejected` в логе). Сервер иногда отдаёт результат
чужого запроса; сборщик повторяет попытку до 6 раз с паузой. Если ошибка постоянная — проверьте
вручную страницу запроса (URL в логе): могли измениться параметры формы или формат выгрузки
(колонки проверяются в `parsers/db_export.validate`).

**Изменилась вёрстка сайта.** Контент страницы ищется в `div#center`, ссылки на файлы —
по шаблону `/file/doc/<id>.<ext>`, опции форм — по `select[name="thid[]"]` и т. п.
(`parsers/pages.py`).

**Нет `textutil` (Linux).** Установите LibreOffice (`soffice`), либо используйте
закоммиченный `data/interim/tnved_2017.csv` — шаг `tnved` можно пропустить.

## Как устроен код

| модуль | ответственность | вход → выход |
|---|---|---|
| `catalog.py` | обход страниц | сайт → `data/raw/pages/`, `data/catalog/` |
| `fetch_files.py` | загрузка файлов | `files.json` → `data/raw/files/` |
| `fetch_db.py` | выгрузка веб-БД | `db_options` → `data/raw/db/`, `db_queries.json` |
| `parsers/*` | разбор форматов, без побочных эффектов | байты/файлы → списки словарей |
| `build.py` | справочники, разрешение кодов, загрузка в DuckDB | `data/raw` + `data/catalog` → `.duckdb` |
| `sql/*.sql` | схема, представления, проверки | — |
| `docs.py` | генерируемая документация | `.duckdb` → `docs/data_dictionary.md`, `docs/inventory.md` |

Принцип: загрузчики только скачивают и сохраняют «как есть»; вся интерпретация — в парсерах
и `build.py`, поэтому любую ошибку разбора можно исправить и пересобрать БД без повторной загрузки.

## Добавление новой таблицы

1. Опишите таблицу и колонки в `sql/schema.sql` (с `COMMENT ON`).
2. Добавьте разбор в соответствующий парсер и загрузку в `build.py` (`insert(con, "<table>", rows)`).
3. При необходимости — представление в `sql/views.sql` и проверку в `sql/qc.sql`.
4. `make build docs test`.
