# Սպասարկում

[English](../en/maintenance.md) | **Հայերեն** | [Русский](../ru/maintenance.md)

## Պարբերական թարմացում

Նոր մեքենայի վրա նախ վերականգնեք վերջին պատկերի հում տվյալները, որպեսզի ամեն ինչ նորից չներբեռնեք (դրանից
հետո `fetch-db`-ը կներբեռնի միայն բացակայողը և վերջին երկու տարիները).

```bash
make install download-raw
```

Այնուհետև.

```bash
make catalog fetch-files fetch-db build docs notebook test
git add -A && git commit -m "data: update to $(date +%F)" && git push
make release            # նոր data-<հավաքման ամսաթիվ> թողարկում՝ բազայով, Parquet-ով և հում տվյալներով
```

* `catalog`-ը կրկին շրջանցում է էջերը երեք լեզվով։ Նոր ֆայլերը և վեբ բազայի ձևերում նոր տարիները հայտնաբերվում
  են ավտոմատ (`data/catalog/files.json`, `data/catalog/db_options/*.json`)։
  Մանիֆեստների փոփոխությունները երևում են `git diff`-ում. սա հարմար միջոց է նկատելու, որ կայքում ինչ-որ բան
  փոխվել է։
* `fetch-files`-ը ներբեռնում է միայն բացակայող ֆայլերը (`--force`-ը բոլորը նորից է ներբեռնում)։ Հեշերը
  `files.json`-ում են։
* `fetch-db`-ը ներբեռնում է բացակայող տարիները և **միշտ** կրկին հարցում է անում վերջին երկու տարիների համար
  (`--refresh-last 2`), քանի որ ընթացիկ և նախորդ տարիները ճշգրտվում են։ Սկավառակի վրա արդեն առկա
  ներբեռնումները վերստուգվում են, անվավերները կրկին են հարցվում։ Կարելի է սահմանափակել՝
  `--nid 148 --lang en --mode annual`։
* `build`-ը վերստեղծում է ամբողջ բազան (մոտ 5 րոպե)։
* Կառուցումից հետո ստուգեք `SELECT * FROM qc_summary` (տե՛ս [data_quality.md](data_quality.md)) և գործարկեք
  `make test`։
* `release`-ը պահանջում է մաքուր աշխատանքային ծառ և push արված `HEAD` (թողարկման պիտակը դրվում է այդ
  commit-ի վրա), ինչպես նաև `gh`՝ `opendataam/arm-ext-trade`-ում գրելու իրավունքով։ Լռելյայն պիտակը
  `data-<վեբ բազային վերջին հարցման ամսաթիվ>` է. եթե այդպիսի թողարկում արդեն կա, նշեք այլ պիտակ՝
  `python -m armstat_trade release --tag ...`։
  Թողարկման նկարագրությունը (ընդգրկում, որակի ստուգումներ) գեներացվում է ավտոմատ (`RELEASE_NOTES.md`)։

Առաջարկվող հաճախականությունը՝ ամսական (ամսական տվյալները հրապարակվում են ~1–2 ամիս ուշացումով, ԱՏԳ ԱԱ
տարեկան ֆայլերը հայտնվում են հաջորդ տարվա ընթացքում)։

## Ինչ անել, եթե…

**Հայտնվել է անհայտ կառուցվածքով նոր ֆայլ.** Ընտանիքը որոշվում է ըստ էջի (`FAMILY_BY_NID`՝ `build.py`-ում)։
Բոլոր բջիջները ամեն դեպքում հայտնվում են `raw_xlsx_cell`-ում։ Եթե 2-նիշ տեղեկագրում հայտնվել է նոր անվանմամբ
թերթ, այն դասակարգվում է `files_hs2.classify_sheet`-ում (լռելյայն՝ `hs2_partner`). անհրաժեշտության դեպքում
ավելացրեք կանոն և թերթի տեսակ։

**Երկրների անվանումները չեն համապատասխանեցվել** (`qc_unresolved_country`, `partner_rows_without_country`)։
Ավելացրեք գրելաձևը `reference.COUNTRY_NAME_ALIASES`-ում (բանալի՝ անվանումը սկզբնաղբյուրում, արժեք՝ երկրի
կոդը)։ Կոդը կարելի է ստուգել վեբ բազային կոնկրետ `thid[]`-ով հարցմամբ։

**Վեբ բազայի ներբեռնումները մերժվում են** (լոգում՝ `export ... rejected`)։ Սերվերը երբեմն վերադարձնում է
ուրիշի հարցման արդյունքը. հավաքիչը կրկնում է փորձը մինչև 6 անգամ՝ դադարով։ Եթե սխալը մնում է, ձեռքով
ստուգեք հարցման էջը (դրա URL-ը լոգում է). հնարավոր է՝ փոխվել են ձևի պարամետրերը կամ ներբեռնման ձևաչափը
(սյունակները ստուգվում են `parsers/db_export.validate`-ում)։

**Փոխվել է կայքի դասավորությունը.** Էջի բովանդակությունը որոնվում է `div#center`-ում, ֆայլերի հղումները՝
`/file/doc/<id>.<ext>` օրինաչափությամբ, ձևերի ընտրանքները՝ `select[name="thid[]"]`-ով և այլն
(`parsers/pages.py`)։

**`textutil` չկա (Linux).** Տեղադրեք LibreOffice (`soffice`) կամ օգտագործեք git-ում պահվող
`data/interim/tnved_2017.csv`-ն. `tnved` քայլը կարելի է բաց թողնել։

## Ինչպես է կազմակերպված կոդը

| մոդուլ | պատասխանատվություն | մուտք → ելք |
|---|---|---|
| `catalog.py` | էջերի շրջանցում | կայք → `data/raw/pages/`, `data/catalog/` |
| `fetch_files.py` | ֆայլերի ներբեռնում | `files.json` → `data/raw/files/` |
| `fetch_db.py` | վեբ բազայի ներբեռնում | `db_options` → `data/raw/db/`, `db_queries.json` |
| `parsers/*` | ձևաչափերի վերլուծություն՝ առանց կողմնակի ազդեցությունների | բայթեր/ֆայլեր → բառարանների ցուցակներ |
| `build.py` | տեղեկատուներ, կոդերի համապատասխանեցում, բեռնում DuckDB | `data/raw` + `data/catalog` → `.duckdb` |
| `sql/*.sql` | սխեմա, ներկայացումներ, ստուգումներ | — |
| `docs.py` | գեներացվող փաստաթղթեր | `.duckdb` → `docs/data_dictionary.md`, `docs/{en,hy,ru}/inventory.md` |
| `release.py` | տվյալների պատկերներ GitHub Releases-ում | `.duckdb`, `data/raw`, `data/catalog` → `data/release/<tag>/` → թողարկում |

Սկզբունք. ներբեռնիչները միայն ներբեռնում և պահպանում են տվյալները «ինչպես կա», իսկ ամբողջ մեկնաբանությունը
կատարվում է վերլուծիչներում և `build.py`-ում, ուստի վերլուծության ցանկացած սխալ կարելի է ուղղել և բազան
վերակառուցել առանց կրկին ներբեռնելու։

## Փաստաթղթերի լեզուներ

Փաստաթղթերը պահվում են երեք լեզվով՝ `docs/en/` (հիմնական), `docs/hy/` և `docs/ru/`, README-ն նույնպես՝
`README.md`, `README.hy.md`, `README.ru.md`։ Փաստաթուղթը փոխելիս թարմացրեք բոլոր երեք տարբերակները։ Տվյալների
բառարանը (`docs/data_dictionary.md`) գեներացվում է անգլերեն՝ `COMMENT ON` նկարագրություններից, իսկ աղբյուրների
ցանկերը (`docs/<lang>/inventory.md`) գեներացվում են յուրաքանչյուր լեզվով `make docs`-ով։

## Նոր աղյուսակի ավելացում

1. Նկարագրեք աղյուսակը և դրա սյունակները `sql/schema.sql`-ում (`COMMENT ON`-ով)։
2. Ավելացրեք վերլուծությունը համապատասխան վերլուծիչում և բեռնումը՝ `build.py`-ում
   (`insert(con, "<table>", rows)`)։
3. Անհրաժեշտության դեպքում ավելացրեք ներկայացում `sql/views.sql`-ում և ստուգում՝ `sql/qc.sql`-ում։
4. `make build docs test`։
